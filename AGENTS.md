# Project Architecture
- Administrative property blocks keep inactive rows and source identities, use an admin-only atomic SQL operation and a write guard; public current/redirected URLs return 410, while sync excludes blocked records and aliases to prevent resurrection.
- The root document initializes React Refresh before application modules in development only; SSR preview HTML does not reliably receive Vite's preamble injection.
- Marketing campaigns are isolated in campaign modules and email_* tables, use Resend only, and default to real sending disabled; transactional Lovable email dispatch remains unchanged. Marketing consent is distinct from privacy consent, and suppression cannot be undone by imports.
- Campaign tests use email_campaign_tests, never contacts or email_sends; admin consent appends an actor/time/reason audit through an authenticated SQL function, preserving suppression. Reserved-domain checks exist both in enqueue SQL and immediately before dispatch to prevent bypasses.
- Property sharing message/UTM and cover sizing live in src/lib/property-sharing.ts; reusable controls load full facts on card click and use the same formatter as the detail page to prevent incomplete or divergent shares.

- Dynamic CMS-created developments render through the shared full development template; this keeps future pages consistent with the MPD development experience.
- Development-specific CMS data lives in editorial_pages.development_details JSON; this keeps the development form structured without fragmenting content across tables.
- Property public SEO text is generated only from structured property facts plus the official condominium reached by condominium_id; this prevents raw scraped labels from leaking into public copy.- Portal and main-site listings are reconciled by source_id (numeric URL tail) in src/lib/reconciliation.server.ts, shared by the daily cron route and the Admin 'Rodar agora'; external_ref paths change when purpose/neighborhood change.
- Leads CRM: all form tables feed public.leads through AFTER INSERT/UPDATE triggers (upsert_lead); forms stay unchanged and new forms only need a trigger.
- /imoveis searches in the database (search_properties RPC + property_search_facets) and loads only the current page; keep its text-matching rules identical to src/lib/property-filter-legacy.ts and verify with scripts/imoveis-parity.ts.
- Listing price formatting and comparisons share src/lib/property-listing.ts; database listing_price/listing_sale_group/listing_rent_price columns order public queries before limits, while condominium responses provide separately server-sorted purpose arrays so tab changes cannot sort only the displayed subset.
- Property card/ficha photos use card_image_url / large_image_url: pre-generated WebP via /api/public/property-thumb (scripts/generate-property-thumbs.py) or, automatically, wsrv.nl URLs set by the properties_auto_thumbs DB trigger whenever the main photo changes; the Worker cannot resize images.
- E-mails de formulário são disparados pelas server functions após gravar (dispatchLeadEmails lê o lead central); textos editáveis em email_template_settings; sends logged in email_dispatch_log.
- External property photos without a pre-generated thumbnail are resized through wsrv.nl via src/lib/img-resize.ts with onError fallback to the original; cdn.uso.com.br has no resize URLs.
- Property photo tools (admin-only) use src/lib/property-photos.functions.ts and the shared PropertyPhotoTools component, gated after hydration by a session-specific checkIsAdmin; property-photo-zip.ts builds ordered code-named ZIPs in batches of five in memory (never stored). "Salvar no acervo" copies originals to the private acervo bucket under {code}/; reconciliation never deletes those files.
- Public card/page photos come from the database computed field card_image (editorial_pages, streets) and src/lib/image-fallbacks.ts never returns bundled images; missing photos render BrandPlaceholder, so photo fallback order lives in one place (SQL) and generic photos can't leak back.
- Radar questionnaire logic lives only in src/components/radar/radar-flow.tsx (page and modal variants); per-objective page copy/slugs live in src/lib/radar-pages.ts, which also feeds sitemap, mapa do site and footer.
- Installable app (PWA): vite-plugin-pwa generateSW emits /sw.js; registration only via src/lib/pwa.ts and only on SITE_HOST (never preview/iframe/dev), so stale caches can't reach the editor.
- PWA and browser icons are static files under public/icons with public/favicon.ico; keep manifest, shortcuts, head links and Workbox precache in sync so uploaded brand icons are used consistently.
- FinancingSimulator has an opt-in standalone mode for the financing page; property-detail defaults stay unchanged, and standalone submissions use the existing financing simulation-to-lead workflow to keep CRM and emails unified.
- Main-site sync uses the Tokko API: src/lib/tokko-sync.server.ts (shared by hourly pg_cron, Admin 'Sincronizar agora') matches by source_id = Tokko ID, falling back to unique reference code; API zeros/nulls never overwrite, so unfilled provider fields can't erase portal data. Rows absent from the API on consecutive runs become inactive with review_status 'saiu_da_api' plus a 301 seo_redirect (note marks it) and come back automatically if they reappear; any existing code/ID blocks re-import, so manual removals stick.
- Sync safety lives in runReconciliation (src/lib/reconciliation.server.ts): deactivation only when the paged fetch is complete and >=95% of the last complete run, max 50 per run (else status 'held' awaiting admin approval), stale 'running' rows become 'stalled'; alerts go through the fixed-recipient 'alerta-sincronizacao' template. Internal codes always follow the API unless manual_overrides.internal_code; old codes go to properties.previous_codes (search alias, never shown), slug unchanged.
- Property titles/H1/seo_title/WhatsApp use internal_code as 'Cód.' (URL number only as fallback) and include bedrooms but never suites; suites > bedrooms are stored/shown empty (safeSuites + apiFactPatch), so bad counts never reach public text.
- Owner-acquisition pages (/anuncie-seu-imovel, /vender-meu-imovel, /alugar-meu-imovel) reuse submitRadarLead with conversion_context captacao_venda/captacao_locacao; the leads_from_radar trigger maps that to CRM source, so no new table is needed.
- Contact page form saves to contact_messages via submitContactMessage (honeypot + signup-guard IP limit), and a trigger feeds leads with source 'contato'.
- Filtro de condomínio de /imoveis é seleção múltipla por condominium_id (slugs na URL ?condo=a,b); equivalência numérica 1/I/Um via public.condo_num_norm (SQL) espelhada em canonicalNumWords (src/lib/property-search.ts) — manter os dois iguais e a paridade com property-filter-legacy.ts.
- Condo linking from Univen "Empreendimento" tag/development lives in src/lib/univen-condo-match.ts (univen_condo_aliases, optionally per usage, then Central names/aliases) and condominiums.usage gates residential/commercial types; unrestricted types accept a unique usage-specific alias, while multiple targets remain ambiguous. Sync only links rows without condo and without manual_overrides.condominium_id/condominium_name, and relinkSlug adds the 301, so automatic linking never overrides manual or existing links.
- Tokko sync: property_type follows the API unless manual_overrides.property_type (API "Terreno" never downgrades "área", which Univen lacks); a type change regenerates slug via relinkSlug with 301, so URLs always match the type.
- Admin navigation lives only in src/lib/admin-nav.ts (groups, routes, descriptions); AdminShell in the _authenticated layout renders it as a sidebar on /admin*, /cms*, /audit* for admins, and the /admin home renders the same list as cards, so new admin routes must be added there. Team access (/admin-equipe) grants the admin role via src/lib/team.functions.ts with the service key; removing access only deletes the role, never the user.
- Broker proposals: admin or corretor creates selections (max 40, 14-day expiry) for a broker_profiles corretor; the public /proposta/$token page (noindex) reads via service-key server functions in src/lib/proposals.functions.ts and always shows current prices/availability, a full ficha per property (src/lib/property-ficha.ts, also used for the WhatsApp summary) and a desktop broker figure (broker_profiles.figure_url, transparent PNG). Tables live in supabase/sql/propostas-corretor.sql (run manually in the Cloud SQL editor); new proposals enter leads via upsert_lead with source 'proposta'.
- App do Corretor (/corretor, PWA 'S.A Corretor' via public/manifest-corretor.webmanifest swapped in by the layout): own login, roles from user_roles ('admin' full, 'corretor' app only) checked by src/lib/staff.server.ts. Leads have owner_user_id/stage (+ lead_notes); all staff see all leads, unowned ones are claimed atomically, only owner/admin edit. Proposal editor is the shared src/components/proposals/proposal-editor.tsx. New-lead Web Push: dispatchLeadEmails → notifyNewLead (src/lib/push.server.ts, once per lead via pushed_at), aes128gcm/VAPID in src/lib/web-push.server.ts, VAPID keys generated server-side into app_private_settings (never in the repo), SW handler public/sw-push.js via workbox importScripts. SQL: supabase/sql/app-corretor.sql.
- /imoveis "Mais filtros" (suítes, estilo, mobília, características): sync stores Tokko tags in properties.features (labels, synonyms/hidden tags in src/lib/property-features.ts), custom tag Categoria in category and furniture tags in furnishing; feature_slugs is a generated column (public.feature_slugs, mirror of featureSlug). search_properties takes p_suites/p_categories/p_furnishing (OR)/p_features (AND by slug); property_more_facets counts each group respecting the others; options need ≥5 ativos; URL ?suites=&estilo=&mobilia=&carac=, carac makes noindex with canonical without it. The legacy boolean furnished stays untouched until the owner approves replacing it.
- End-of-page CTAs: ResolvedCta resolves page legacy text → page cta_id → rule keys (condominio:residencial|comercial by condominiums.usage, blog|guia:{morar,negocios,educacao,lazer} via ctaPillarGroup, lista:{residencial|comercial}-{venda|aluguel}) → content type → 'site', all configured in cta_blocks/cta_defaults via /admin-ctas; {condominio}/{bairro}/{rua}/{titulo} in CTA text are filled per page. Rendered on blog, guia, condomínio, rua, bairro, tema and /imoveis-alphaville pages; condo pages use the owner-acquisition CTA (legacy condo CTA texts backed up in editorial_cta_backup_20261120).
- Neighborhood guides (/guia/$slug with editorial_pages.area_filter) reuse the street model through RPC area_overview + AreaOverviewBlock (numbers, condos, streets, map, nearby, ficha kind "bairro") and computedAreaFaq.
- Street pages (/ruas/$slug): one hub at /guia-de-ruas (/ruas/ and the old /guia-de-ruas-alphaville module 301). Page shows live numbers + condos (RPC street_overview), Google Maps embed by name, streets.nearby (aggregated from condominiums.nearby of the street's condos), stored + computed FAQ (src/lib/street-overview.ts), and a PDF ficha (jsPDF in the browser, src/lib/street-ficha-pdf.ts) unlocked by name+e-mail+WhatsApp → lead source 'ficha' (src/lib/guide-leads.functions.ts, GuideDownloadLead component, reusable for bairro/condomínio).
- Condo map: public page /mapa (src/routes/mapa.tsx, in the menu and sitemap) embeds the static live map public/mapa-prototipo.html?embed=1 in an iframe; the HTML stays noindex. In embed mode it posts map_condo_open / map_property_click to the parent, which forwards them to gtag. Positions come from condo_map_points (?ajustar=1 as admin to drag).
- Street CEPs: streets.ceps (jsonb) holds official Correios CEPs fetched from ViaCEP (tipo geral = street/stretch, numero = building with its own CEP). /ruas/$slug shows a CEP box at the top, puts the CEP in the title/description, adds "Qual é o CEP da X?" to the FAQ and postalCode to the schema (src/lib/street-ceps.ts). Never type CEPs by hand or copy them from CEP sites; fetch them from ViaCEP.
- Condo map v2 (2026-11-23): /mapa embeds public/mapa-condominios.html (MapLibre GL 4.7.1 from unpkg + OpenFreeMap "dark" style, free, no key). Territories/municipal border are GeoJSON layers; bubbles are HTML inside the canvas container positioned with map.project. Filters: purpose (Todos/Venda/Locação) + one "Tipo" button (Apartamentos/Casas/Terrenos/Comerciais, with counts), kept in the URL (?f=v&tipo=apto, also on the parent /mapa URL). The panel shows type chips only when the condo has more than one type. Every future map-search module must reuse these same two filters and buckets (tipoOf). The old SVG version stays at /mapa-prototipo.html.
- Map satellite: "Mapa | Satélite" toggle in public/mapa-condominios.html uses Esri World_Imagery raster tiles (ibasemaps-api.arcgis.com/.../World_Imagery/MapServer/tile/{z}/{y}/{x}, 256px; the static-basemap-tiles service has no imagery) with a public API key (ESRI_KEY) from the ArcGIS Location Platform account "saimoveis" (item "Mapa S.A - satelite"). The key only has the Basemaps privileges, is restricted to the referrers portal.saimoveisalpha.com.br and alphaville-vantage.lovable.app, pay-as-you-go is OFF (free tier only), and it EXPIRES 22/11/2027: regenerate it in the item page and replace ESRI_KEY before then. ?base=sat opens in satellite.
- Map avenue tour ("Passeio"): public/mapa-condominios.html has ROUTES (one-direction OSM polylines per avenue, fetched via Overpass in a browser and simplified) and a tour that flies the camera along the line (pitch 62, ~48 m/s, slows near condos). Stops = condos whose bubble/territory is within 170 m of the line; only those bubbles show during the tour. ?passeio=<slug> starts it (also from the parent /mapa URL). To add an avenue, append its polyline to ROUTES.
